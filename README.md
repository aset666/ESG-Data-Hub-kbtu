# ESG Data Inventory System (ESG Data Hub)

Централизованная система-инвентарь (каталог) всех ESG-данных университета — единая
«карта» источников, метрик, владельцев и мест хранения. Основа data governance для
ESG-отчётности (STARS, QS Impact, THE, GRI, CSRD и др.).

## Стек

- **Frontend:** Next.js 14 (App Router) + TypeScript + Tailwind CSS
- **Backend:** FastAPI (Python) + SQLAlchemy
- **База данных:** PostgreSQL 16
- **Авторизация:** JWT, роли `admin` (полный CRUD) / `viewer` (только просмотр)
- **Контейнеризация:** Docker + Docker Compose

## Быстрый запуск (Docker Compose)

```bash
git clone <repo_url>
cd esg-data-hub
cp .env.example .env        # при необходимости отредактируйте
docker compose up --build
```

После запуска:

- Frontend: http://localhost:3000
- Backend API: http://localhost:8000 (документация: http://localhost:8000/docs)
- PostgreSQL: localhost:5432

При первом запуске backend-контейнер автоматически создаёт таблицы и заполняет базу
демонстрационными данными (41 ESG-запись + 2 пользователя), если база пуста.

## Модель данных

Каждая ESG-запись состоит из 4 связанных блоков (согласно ТЗ):

1. **Метрика** (`metrics`) — блок E/S/G, категория, название, определение, единица
   измерения, соответствие стандартам (GRI/SASB/TCFD/SDGs/STARS), Scope 1/2/3, статус
   сбора (собирается / частично / не собирается / планируется).
2. **Источник данных** (`sources`) — тип источника, система/файл, частота обновления,
   формат.
3. **Ответственные** (`responsibles`) — подразделение-владелец, ответственный за сбор,
   контакты, уровень доступа (публичный/внутренний/чувствительный).
4. **Хранение и качество** (`storage_quality`) — место хранения, дата последнего
   обновления, оценки качества (полнота/точность/своевременность, 1–5), проблемы
   (дубликаты, ручной ввод, отсутствие автоматизации и т.д.).

Плюс `users` (пользователи и роли) и `audit_log` (журнал изменений: кто/когда/что
создал, изменил или удалил).

## Функциональность

- Веб-приложение: read-only для наблюдателей, полный CRUD для администраторов
- Поиск (по названию/определению/категории) + фильтры (блок ESG, статус, подразделение,
  стандарт) + сортировка
- Адаптивный дизайн (мобильный просмотр)
- Авторизация по email/паролю с ролями
- Два режима отображения каталога: таблица и карточки
- **Heatmap / карта пробелов** — покрытие сбора данных по подразделениям и блокам E/S/G
- **Экспорт в Excel** — полная выгрузка каталога (`ESG_Data_Landscape_*.xlsx`)
- **Журнал изменений** — кто и когда создал/изменил/удалил запись
- Страница «О системе» с методологией заполнения и глоссарием терминов

## Локальная разработка без Docker

### Backend

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
# поднимите PostgreSQL локально и создайте БД esg_data_hub / пользователя esg_user
cp .env.example .env   # отредактируйте DATABASE_URL под ваш локальный Postgres
python -m app.seed     # создаст таблицы, пользователей и демо-данные
uvicorn app.main:app --reload --port 8000
```

### Frontend

```bash
cd frontend
npm install
NEXT_PUBLIC_API_URL=http://localhost:8000 npm run dev
```

## Как добавить свои реальные данные

1. Войдите под администратором.
2. Нажмите **«+ Новая запись»** в шапке (или откройте `/metrics/new`).
3. Заполните 4 секции формы: метрика → источник → ответственные → хранение/качество.
4. Повторите для каждой метрики, которую собирает университет (энергетика, ЖКХ, HR,
   приёмная комиссия, волонтёрский центр, учебный отдел и т.д. — см. раздел
   «Источники данных для заполнения» в ТЗ).
5. Массовое заполнение: можно последовательно вызывать `POST /api/metrics` (см.
   `/docs` для схемы запроса) — например, скриптом из существующего Excel/CSV.
6. Проверяйте прогресс на странице **Heatmap** — она сразу покажет, по каким
   подразделениям и блокам E/S/G остаются пробелы.
7. Когда данные готовы — выгрузите отчёт кнопкой **«Экспорт в Excel»** на главной
   странице.

## API

Полная интерактивная документация (Swagger UI) доступна на `/docs` после запуска
backend, например http://localhost:8000/docs. Ключевые эндпоинты:

| Метод | Путь                      | Описание                              | Доступ         |
|-------|---------------------------|----------------------------------------|----------------|
| POST  | `/api/auth/login`         | Вход, получение JWT                    | все            |
| GET   | `/api/auth/me`            | Текущий пользователь                   | авторизован    |
| POST  | `/api/auth/users`         | Создать пользователя                   | admin          |
| GET   | `/api/metrics`            | Список записей (фильтры, поиск)        | авторизован    |
| POST  | `/api/metrics`            | Создать запись                         | admin          |
| PUT   | `/api/metrics/{id}`       | Обновить запись                        | admin          |
| DELETE| `/api/metrics/{id}`       | Удалить запись                         | admin          |
| GET   | `/api/stats/heatmap`      | Данные для карты пробелов              | авторизован    |
| GET   | `/api/stats/summary`      | Сводная статистика                     | авторизован    |
| GET   | `/api/export/excel`       | Выгрузка каталога в Excel              | авторизован    |
| GET   | `/api/audit-log`          | Журнал изменений                       | авторизован    |

## Тестирование, проведённое перед сдачей

- Backend: локально поднят PostgreSQL, выполнен полный цикл — миграция схемы,
  сидирование 41 записи, вход под admin/viewer, все фильтры (`block`, `status`,
  `department`, `standard`, `search`), создание/обновление/удаление записи под admin,
  проверка запрета (403) на запись под viewer, генерация и валидация Excel-файла,
  проверка записи событий в журнал изменений.
- Frontend: `npm run build` проходит без ошибок TypeScript/ESLint, standalone-сборка
  запущена и проверена (`node server.js`) вместе с работающим backend — все страницы
  (`/login`, `/`, `/about`, `/heatmap`, `/audit-log`, `/metrics/[id]`, `/metrics/new`)
  отдают HTTP 200.
